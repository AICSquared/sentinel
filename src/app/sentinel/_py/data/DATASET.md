| | |
|---|---|
| **Source** | Our own: generated by `_py/make_dataset.py` (seed 7) |
| **Licence** | Ours, same as this repo. No third-party data is included |
| **Synthetic** | Yes, fully synthetic |
| **Rows** | 997: 598 clean, 173 prompt_injection, 76 tool_misuse, 75 data_exfiltration, 75 privilege_escalation. These counts include 12 junk rows, which keep their source row's label |

Regenerate with `cd src/app/sentinel/_py && python make_dataset.py`. The same seed gives the same file. It also writes `baselines.json`: the MEDIAN `distinct_tools_used` per role on clean rows, which `features.RowBuilder` uses for column 6.

## Why not Kaggle

We checked [AI Agent Cybersecurity Dataset 2026](https://www.kaggle.com/datasets/chuneeb/ai-agent-cybersecurity-dataset-2026) (Uneeb Zulfiqar, v1, updated 2026-06-25, read through the Kaggle API on 2026-11-14) against the 4 checks in issue #6:

| check | result |
|---|---|
| (a) licence allows our use | pass: CC BY 4.0 |
| (b) synthetic or real | a curated mix: real threat intel (AlienVault OTX, NVD CVEs, CISA KEV, a Hugging Face prompt-injection set) plus small hand-made tables |
| (c) columns map onto contract A | **fail**: 22 small CSVs of CVEs, attack taxonomies, jailbreak prompts and incident write-ups. There is no per-agent action telemetry, so nothing maps to `actions_per_min`, `distinct_peers`, `bytes_out_per_min` and the other inputs |
| (d) labelled with attack types per window | **fail**: labels are incident or technique categories, not per-agent-window `attack_type` |

Two checks failed, so per issue #6 we generate our own.

## How it is generated

`make_dataset.py` simulates the swarm at the contract-A0 event level (the same JSON the agents POST to `/events`), then turns the events into rows with `features.RowBuilder`. The training data and the live overseer therefore use one feature implementation.

- **Clean agents** (2 per role) act about 9-15 times a minute inside `ROLE_SCOPES`, mostly message 1-2 usual partners, fail about 3% of calls, and sometimes have a busy spell at double speed. Rarely, a harmless out-of-scope read happens.
- **Attacks:** one agent per attack run turns rogue at a random time between 20 s and 40 s, at a random intensity of 0.35-1.0, so some attacks are loud and some are subtle:
  - `prompt_injection`: often touches a `decoy:` credential first, then messages 2-7 peers (half of them to its usual partner) and runs a few risky tools. It **spreads**: a peer that receives 4+ infected messages within the window may turn rogue itself a few seconds later (3 of the 10 runs have a second infected agent).
  - `tool_misuse`: many unusual tools (`shell.exec`, `net.scan`, `fs.delete`, ...) at high speed, with about 45% failures.
  - `data_exfiltration`: reads out-of-scope data (`db:customers`, `mail:inbox`, ...) and posts 15-150 KB chunks outward.
  - `privilege_escalation`: repeated `iam.assume_role` / `sudo` / `secrets.read` on admin resources, with about 50% denied, sometimes after a decoy root token.
- **Labels:** a row (one agent, one 60 s window, every 2 s) gets the attack type when its window holds at least one malicious event from that agent; otherwise `clean`. `unknown` is never a label.
- **`sec_since_normal`:** live, `api.py` derives it from the previous score, so it depends on the detector. The generator uses a stand-in detector that flags an attack 1-4 ticks late and misses half of the subtle ones, so the model can't learn the feature as a shortcut. Clean rows always have 0, and never touch a decoy, which keeps IsoForest #2's baseline clean.
- **Sampling:** every row from all runs (16,213), then a random sample per label (590 clean, 170 prompt_injection, 75 per other type) before the junk rows are added.
- **Junk rows (12):** corrupted copies of real rows. Four have a NaN (dropped by `features.load_dataset`, since no model can score them), four have negative rates and four have impossible magnitudes (about 10,000 actions/min, GB/min outbound). The last two kinds are left for IsoForest #1 (`model_anomaly.filter_train`) to remove.

## Limits

- Synthetic: the attack shapes are our assumptions about how each attack looks in these ten features, not measurements of real hijacked agents.
- `privilege_escalation` overlaps with `prompt_injection` and `data_exfiltration` in these features (all touch out-of-scope or decoy resources, and none of the ten inputs sees which tool was called), so its per-type recall is low. Attack-vs-clean detection is not affected.
- With about 1,000 rows, each attack type has only 3 held-out runs, so per-type numbers move a lot between splits. Read them as rough.
